# 机加工报价辅助 MVP

Status: ready-for-agent

## Problem Statement

服务型机加工厂的**报价员**每天收到客户发来的一批**零件图**（PDF 或图片），必须先把每张图看懂，再把**标题栏**里的图号、零件名称、材料、数量，以及图面上驱动成本的**关键尺寸**与公差手工抄进自己的**报价底稿**，最后凭经验判断这件东西难在哪、要不要上浮价格。

这个过程有三个痛点：

1. **抄写和找数占掉了大部分时间。** 真正需要人的是报价判断，但报价员的时间大量花在"把图上的数字搬到表格里"这种确定性劳动上。询价响应慢，直接丢单。
2. **图纸质量参差。** 约一半是规范的 PDF，另一半是扫描件、手机拍照、微信截图。糊图看得慢，还容易看错。
3. **看漏一项的代价极高。** 漏掉一个 IT6 的严公差、一个深径比超过 5 的深孔、一处薄壁，报价就会偏低，接下来就是亏本干活。而这种错误在报出去之前几乎没有人会复查。

报价员不缺判断力，缺的是"把图上的数快速、可靠地变成结构化的一行"。

## Solution

一个"AI 预填 + 人工快速确认"的报价辅助工具。报价员上传**零件图**，系统完成**读图取数**并预填出结构化结果，报价员在表单与原图并排的界面上快速**复核**，确认后归入**报价任务**并一键导出**报价底稿**。

产品对使用者的承诺被刻意收窄成三句话：

- **我们替你抄写，不替你判断。** 只做取数（标题栏字段、**关键尺寸**与公差、技术要求），不估工时、不定价、不排工艺（ADR-0001）。
- **我们对把握程度诚实。** 上传后先给整张图一个**图纸质量分级**，差图直接劝退并建议走人工；**高风险字段**（尺寸、公差）无论图纸多清晰一律标"需确认"（ADR-0002）。
- **我们只报发现的疑似风险，永远不说"没风险"。** **风险标签**由规则引擎基于已提取数据算出，可解释、可调；空结果表达的是"未发现可判定的风险项"，绝不是"此件安全"（ADR-0007）。

对外的价值主张是"**少抄写、看得更快**"，不是"不用看图"（ADR-0004）。

## User Stories

### 上传与图纸质量分级

1. 作为**报价员**，我想把一张**零件图**（PDF 或图片）拖进上传区，以便立刻开始**读图取数**，不用先转格式。
2. 作为**报价员**，我想一次选中多张**零件图**批量上传，以便对应真实场景里客户一次发来一整包图。
3. 作为**报价员**，我想在上传超出大小或页数限制的文件时立刻看到明确的拒绝原因和限制数值，以便我知道该怎么处理而不是反复重试。
4. 作为**报价员**，我想上传多页 PDF 时明确知道系统只处理我指定的那一页（默认第 1 页），以便结果和我的预期一致。
5. 作为**报价员**，我想在上传后立刻看到这张图的**图纸质量分级**（清晰 / 一般 / 差），以便我在花时间之前就知道这张图值不值得让 AI 来做。
6. 作为**报价员**，当**图纸质量分级**为"差"时，我想系统直接劝退并建议我走人工，而不是硬给我一份看起来很自信的错结果，以便我不被误导。
7. 作为**报价员**，当一张图被判为"差"但我确信它可读时，我想有一个明确的"仍然继续"入口，以便我保留最终决定权；同时这份结果要一直带着"低质量图，结果不可靠"的标记。
8. 作为**报价员**，我想知道**图纸质量分级**只表示图纸本身的质量、不代表结果可以免核，以便我不会把"清晰"误解成"不用看了"。
9. 作为**报价员**，我想上传的是装配图或爆炸图时被明确告知不在处理范围，以便我不浪费时间等一个注定错的结果。
10. 作为**报价员**，我想在提取进行中看到进度状态，以便我知道是在跑还是卡住了。
11. 作为**报价员**，当提取因外部原因失败时，我想看到失败原因并能一键重试，以便不用重新上传。
12. 作为**报价员**，我想重试提取时已经做过的**复核**修改不被覆盖，以便我不用重做一遍已经确认过的部分。

### 读图取数

13. 作为**报价员**，我想系统自动提取**标题栏**里的图号、零件名称、材料、数量，以便这些每张图都要抄的字段不再手输。
14. 作为**报价员**，我想系统提取驱动成本的**关键尺寸**与公差（最严公差、最大外形、最深孔、最薄壁等），以便我拿到报价判断真正需要的输入。
15. 作为**报价员**，我想系统提取图面上的技术要求（热处理、表面处理、粗糙度等），以便这些常被忽略但影响成本的条目不被漏掉。
16. 作为**报价员**，我想系统**不**试图还原全图所有标注，以便我不用去核对一屏我根本不关心的尺寸。
17. 作为**报价员**，我想每一项提取结果都能看到它属于哪一类字段（标题栏字段 / **关键尺寸** / 技术要求），以便我按类别快速扫过。
18. 作为**报价员**，我想图上确实没有的字段被如实留空，而不是被编造一个看起来合理的值，以便空值本身就是一个可信的信号。
19. 作为**报价员**，我想在提取结果旁边一直看到"本工具不替代看图，请重点复核公差密集区与技术要求"的提示，以便我不会因为界面太顺手而放弃自查。
20. 作为**报价员**，当这张图属于**目标零件族**时，我想系统用针对该族的方式来取数，以便准确率更高。
21. 作为**报价员**，当这张图不属于**目标零件族**时，我想结果被明确标注为"实验性、不保证"，以便我知道要更谨慎，同时我仍然能用它。

### 风险标签

22. 作为**报价员**，我想看到系统基于已提取数据算出的**风险标签**（高精度、深孔、薄壁、细长等），以便我在定价时不漏掉加工难点。
23. 作为**报价员**，我想每个**风险标签**都能展开看到它是被哪条规则、由哪个提取值触发的，以便我能判断这个提醒是不是误报。
24. 作为**报价员**，我想**风险标签**永远只表达"发现的疑似风险，请复核"，以便我不会因为看到"无风险"而不上浮报价。
25. 作为**报价员**，当系统一个**风险标签**都没算出来时，我想界面写的是"未发现可判定的风险项，不代表此件无风险"，以便沉默不被读成安全。
26. 作为**报价员**，我想在我修正了某个**关键尺寸**之后**风险标签**跟着重算，以便标签始终反映我确认过的数据而不是 AI 的原始输出。
27. 作为**报价员**，我想**风险标签**是规则算出来的而不是 AI 直接判断的，以便同样的数据永远得到同样的标签。
28. 作为**管理员**，我想看到当前生效的风险规则清单及其阈值，以便我知道系统在按什么标准提醒。
29. 作为**管理员**，我想调整风险规则的展示优先级，以便本厂最在意的风险排在最前面。

### 复核

30. 作为**报价员**，我想在同一个屏幕上左边是提取结果表单、右边是原图，以便我核对时不用来回切窗口。
31. 作为**报价员**，我想能在原图区自由缩放和平移，以便我看清扫描件上的小字。
32. 作为**报价员**，我想**高风险字段**（尺寸、公差）无论**图纸质量分级**如何都被标为"需确认"，以便最贵的错误有一道强制关卡。
33. 作为**报价员**，我想低风险字段（图号、名称等）在清晰图上不强制我逐个点确认，以便复核的重点落在真正危险的地方。
34. 作为**报价员**，我想逐项确认或直接就地修改提取值，以便修正不需要跳转页面。
35. 作为**报价员**，我想把某一项标记为"忽略"，以便图上不适用的条目不会一直挡着我完成复核。
36. 作为**报价员**，我想手工补录一条 AI 完全没提出来的**关键尺寸**，以便漏提的项也能进入最终结果。
37. 作为**报价员**，我想在所有"需确认"项都处理完之前无法把这张图标记为"已复核"，以便强制复核规则不能被顺手绕过。
38. 作为**报价员**，我想清楚看到还剩几项待处理，以便我知道离完成还有多远。
39. 作为**报价员**，我想我的修改被自动保存，以便刷新或断网不会让我白干。
40. 作为**报价员**，我想把一张图标记为"已复核"后它成为可追溯的报价依据，以便事后出问题能查到当时确认的是什么。
41. 作为**报价员**，我想在标记"已复核"之后仍能重新打开修改，同时留下改动痕迹，以便纠错不需要推倒重来。

### 报价任务与报价底稿

42. 作为**报价员**，我想把多张**零件图**的提取结果归入同一个**报价任务**，以便对应客户一次询价里的多个零件。
43. 作为**报价员**，我想给**报价任务**起名并记录客户名称，以便我在历史记录里能找到它。
44. 作为**报价员**，我想把一张已上传的**零件图**移入或移出某个**报价任务**，以便归错了可以改。
45. 作为**报价员**，我想一键导出整个**报价任务**的**报价底稿**（每个零件一行），以便我直接拿去内部核算或对外报价。
46. 作为**报价员**，我想导出的**报价底稿**长得就像我们厂现在用的那份表，以便我不需要再手工搬一次列。
47. 作为**报价员**，我想在**报价底稿**里看到每个零件的**风险标签**，以便定价时这些提醒不会在导出环节丢失。
48. 作为**报价员**，我想导出时包含非**目标零件族**的"实验性、不保证"标记，以便下游看表的人知道哪几行需要更谨慎。
49. 作为**报价员**，我想在**报价任务**里还有未完成**复核**的零件时导出被拦下或至少被明确警告，以便我不会把半成品发出去。
50. 作为**报价员**，我想在历史记录里按客户、时间、状态找到过去的**报价任务**，以便我能复用或追溯。

### 权限与账号

51. 作为**管理员**，我想为本厂的**报价员**创建账号，以便他们各自登录使用。
52. 作为**报价员**，我想默认只看到自己处理的**零件图**与**报价任务**，以便同事之间的数据互不干扰。
53. 作为**管理员**，我想查看全厂所有处理记录，以便我掌握团队的工作量与结果质量。
54. 作为**管理员**，我想配置本厂的常用材料与**风险标签**优先级，以便系统贴合本厂习惯。
54a. 作为**管理员**，我想**报价底稿**的字段模板由团队在 onboarding 时按我们现有的表配好，而不是让我自己在界面上映射字段，以便我不用理解一套配置概念就能拿到贴合的表。
55. 作为**报价员**，我想我看不到其他工厂的任何数据，以便客户图纸的保密边界成立。

### 度量与验证

56. 作为**管理员**，我想系统自动记录每张**零件图**从"上传"到"已复核"的**处理耗时**，以便我用客观数据判断这工具到底省没省时间。
57. 作为**管理员**，我想录入几条纯人工作业的计时作为基线，以便**处理耗时**有对照才有意义。
58. 作为**管理员**，我想看到本厂的**处理耗时**与人工基线的对比，以便续费决策有依据而不是凭印象。
59. 作为**管理员**，我想看到全厂的**修正记录**统计（哪类字段最常被改），以便我知道 AI 在哪些地方还不靠谱。
60. 作为产品团队，我想每一次对提取结果的修改都被留痕为**修正记录**（原值 → 新值 + 字段类型 + 时间 + 操作人），以便积累数据驱动提示词与后处理规则迭代。

### 保密

61. 作为**管理员**，我想明确知道图纸上传到哪里、由谁处理、是否会被用于训练，以便我能回答我自己客户的保密质询。
62. 作为**管理员**，我想能导出或删除本厂的全部数据，以便合作终止时数据可以带走或清除。

## Implementation Decisions

### 仓库与服务划分

拆成两个库：

- **后端（Python）**：承载全部领域逻辑——**读图取数**编排、**图纸质量分级**、信任规则、**风险标签**规则引擎、**复核**状态流转、**报价任务**归集、**报价底稿**导出、**修正记录**、**处理耗时**埋点、权限。对外暴露 HTTP API。
- **前端（Next.js + TypeScript + Tailwind）**：只做界面与交互，包括上传、并排**复核**页、**报价任务**列表与导出入口、管理员配置页。服务端部分只作为 BFF 代理转发到后端 API，不承载领域规则。

这样划分的原因：所有值得测的行为都在后端，前端保持薄，缝 1 才能覆盖住产品的绝大部分风险。任何"前端算一下就行"的诱惑（例如在浏览器里判断某个字段要不要标"需确认"）都要拒绝——那会把不变量分裂到两个库里。

### 技术栈

| 位置 | 选型 |
| --- | --- |
| 后端框架 | FastAPI |
| 后端包管理 | uv |
| 后端测试 | pytest |
| 数据库 | Postgres |
| ORM / 迁移 | SQLAlchemy + Alembic |
| 对象存储 | 阿里云 OSS |
| 前端 | Next.js + TypeScript（禁用 `any`）+ Tailwind，pnpm 管理依赖 |
| 多模态大模型 | **未定**，见下方"提取引擎"与 Further Notes |

选 FastAPI 有两条与本 spec 直接相关的理由：一是 ASGI 测试客户端能直接打进应用而不用起真实网络端口，缝 1 的集成测试因此成本很低；二是提取引擎返回的结构化结果需要严格校验（模型会编造字段、会给出类型不对的值），Pydantic 正好把这层校验放在适配器边界上，让领域层拿到的永远是已校验的数据。

对象存储虽然定为阿里云 OSS，后端仍通过一个窄接口访问（存、取、签发临时访问 URL、删），不在用例层直接引用 SDK。原因是 ADR-0005 把私有化部署列为后续选项，届时存储后端必然要换。

### 后端分层

自外向内四层，依赖只能向内：

- **接口层**：HTTP 路由、请求响应模型、认证、租户解析。不含业务判断。
- **用例层**：一个用例一个入口（上传零件图、触发提取、确认单项、修正单项、标记已复核、归入报价任务、导出报价底稿、录入人工基线…）。事务边界在这里。**这是缝 1 的位置。**
- **领域层**：纯逻辑，无 IO。包含风险规则引擎、高风险字段判定表、复核完成条件、状态机合法迁移。**风险规则引擎是缝 2 的位置。**
- **适配器层**：提取引擎、对象存储、数据库、导出文件生成。

### 提取引擎作为可替换的 Port

用例层只依赖一个抽象接口：输入是（图像/PDF 页、零件族标识），输出是结构化提取结果 + 图纸质量分级信号。有两个实现：

- 生产实现：境内合规多模态大模型（ADR-0003、ADR-0005）。**具体供应商尚未选定**——硬门槛是数据存境内、书面承诺不用于训练、可签 DPA，三者缺一票否决，且这三条先于识别效果，因此必须先核实条款而不是先比效果。选型走独立调研，结论另立 ADR。
- 测试实现：fixture 驱动的假引擎，按输入图的标识返回预置结果。**这是缝 1 能成立的关键**，也是唯一被替换掉的外部依赖。

供应商未定不阻塞开发：先用假引擎把主干跑通，生产实现只需满足同一个 Port。模型返回结果在适配器边界上做严格校验，校验不通过按提取失败处理，不让脏数据进入领域层。

提示词按**目标零件族**分模板管理，族类作为参数传入引擎，而不是散落在调用点。

### 图纸质量分级与信任模型

分级是**整图级**的三档（清晰 / 一般 / 差），不做逐字段置信度（ADR-0002）。差图走劝退分支，报价员可显式覆盖继续，但结果永久携带低质量标记。

**高风险字段**判定是一张按字段类型的静态表，不是模型输出：尺寸类、公差类 → 强制"需确认"；图号、零件名称、材料、数量等 → 在"清晰"图上不强制。这张表是领域层的常量，被缝 1 与缝 2 共同覆盖。

分级只影响低风险字段是否免确认，**永远不影响高风险字段**——"清晰图上个别错读公差"这个缝隙必须被堵死。

### 零件图状态机

`已上传 → 分级中 → 已分级 → 提取中 → 已提取 → 复核中 → 已复核`，外加两条分支：分级为"差"时进入 `建议人工`（可被显式覆盖回主干），提取失败进入 `提取失败`（可重试回 `提取中`）。

`已复核` 的迁移前置条件是"不存在未处理的需确认项"，这个条件写在领域层，任何用例都绕不过去。`已复核` 之后允许重新打开，但改动进入**修正记录**。

### 风险标签规则引擎

纯函数：输入是当前**已确认**的结构化数据，输出是标签列表，每个标签带触发规则标识、触发值、人类可读理由。规则形如"公差 ≤ IT6 → 高精度"、"孔深/孔径 > 5 → 深孔"（ADR-0007）。

两条硬不变量，写进类型与测试：

1. 输出词表里**不存在**任何表达"安全 / 无风险 / 通过"语义的标签。空列表就是空列表，语义由展示层固定文案承担（"未发现可判定的风险项，不代表此件无风险"）。
2. 引擎无 IO、无随机、无时间依赖，同输入同输出。

报价员修正数据后重算，即标签始终由确认后的值驱动，而非模型原始输出。

### 报价任务与报价底稿导出

**报价任务**是搭在单图之上的**轻量归集层**，不是订单实体：它只负责把多张图的结果归到一起并汇总导出，不含金额、不含状态审批流。单图可以不属于任何报价任务而独立存在。

导出为每个零件一行的表格（xlsx / csv）。字段映射按工厂存一份模板配置，**onboarding 时由团队手工配好**——MVP 不做用户自助的映射 UI（"服务代替功能"）。导出内容必须包含**风险标签**与非目标族的实验性标记。

**管理员配置页里没有导出模板这一项。** 管理员能配的只有常用材料与**风险标签**优先级。模板是一份由团队维护的后台配置，不经过产品界面。这条是有意的取舍：字段映射 UI 要引入一整套映射概念（源字段、目标列、缺省值、顺序），成本高且每家工厂只用一次；换成 onboarding 时人工配好，既完美贴合又不背这套 UI。

### 修正记录

每次对提取值的修改写一条不可变记录：字段标识、字段类型、原值、新值、操作人、时间、所属零件图。用途明确为积累数据 + 驱动提示词/规则迭代，**不做实时模型优化**（ADR-0003）。

### 处理耗时

每次状态迁移写一条带时间戳的事件，**处理耗时**由"上传"与"已复核"两个事件的时间戳算出，各阶段时长可分解。人工基线单独一张表由管理员录入。这是 ADR-0006 给产品加的硬需求：**每次处理必须留关键时间戳**，不能事后补。

### 权限与租户

两档角色：**管理员** / **报价员**，不做细粒度权限。所有数据以工厂为租户边界隔离，租户过滤在用例层统一施加，不依赖调用方传参。

### 成本与保密约束

上传限制单文件大小与 PDF 页数上限（控 API 调用成本）。零件图存阿里云 OSS 并开启服务端加密，Bucket 不允许公共读，前端取图走后端签发的短时效临时 URL。调用日志不落图像内容。大模型供应商与 OSS 应选同一境内区域，避免图纸跨区流动带来额外的合规解释成本。私有化部署不实现，仅作为销售话术记录意向（ADR-0005）。

## Testing Decisions

### 什么是好测试

只测外部可观察的行为：给用例层一个输入，断言它对外产生的结果（返回值、持久化后可再次读到的状态、导出文件的内容）。不断言内部调用了哪些函数、不 mock 领域对象、不对数据库表结构做断言、不给 UI 打快照。测试名字用 `CONTEXT.md` 的术语写（"差图不自动预填"、"高风险字段在清晰图上仍需确认"），不用实现术语。

### 缝 1：后端用例层集成测试

用 pytest 加 FastAPI 的 ASGI 测试客户端直接打进应用（不起真实网络端口），走真实的持久化与真实的风险规则引擎，**唯一被替换的是提取引擎**（换成 fixture 驱动的假实现）。对象存储在测试里指向本地临时目录的窄接口实现——它不承载任何领域行为，替换它不会削弱测试。覆盖的行为包括但不限于：

- 上传一张 fixture 图，走完提取，结果里包含预置的标题栏字段与关键尺寸。
- 分级为"差"的图不自动预填，返回建议人工；显式覆盖后可继续，且结果携带低质量标记。
- 无论分级为"清晰"还是"一般"，尺寸与公差字段一律标为需确认。
- 存在未处理的需确认项时，标记"已复核"被拒绝。
- 修正一个关键尺寸后重新读取，风险标签随之变化。
- 修正产生一条修正记录，原值与新值都对。
- 上传与标记已复核两个时间戳都存在，处理耗时可算出。
- 一个报价任务导出的底稿，行数等于零件数，且包含风险标签列。
- 报价员读不到别的报价员的数据；管理员能读到全厂的。
- 非目标零件族的结果带实验性标记，且该标记出现在导出里。

用真实的 Postgres（容器化），不换 SQLite 替身——替身会让"事务边界正确"和"租户过滤真的生效"这两个真实风险测不出来，而这恰恰是最不能出错的地方。Alembic 迁移在测试启动时真实跑一遍，顺带保证迁移本身可用。

### 缝 2：风险标签规则引擎纯函数测试

表驱动参数化：每条规则一组"刚好触发 / 刚好不触发 / 边界值"用例。加上两条不变量测试：

- 对任意输入，输出中不含表达"安全/无风险"语义的标签（遍历规则输出词表断言）。
- 同一输入重复调用结果完全一致。

单独开这个缝、而不是全从缝 1 打，是**刻意的例外**：规则是组合爆炸的，从 HTTP 层构造每一种公差/孔深组合会让用例臃肿到没人愿意维护，而这里恰好是一个真正的纯函数，测起来没有任何 IO 成本。除此之外不再增加第三个缝。

### 明确不建立的缝

- **不做 UI 端到端测试**。前端保持薄，把可测逻辑全部留在后端；UI 靠人工验收。
- **不在默认测试集里调用真实大模型**。供应商契约测试单独打标记、手动运行，用于换供应商时验证输出契约，不进 CI。
- **不测适配器内部**（对象存储、文件生成库），它们通过缝 1 被间接覆盖。

### Prior art

这是一个尚无代码的仓库，没有既有测试可参照。因此**本 spec 同时确立测试风格**：后续所有功能默认从缝 1 进，新增缝需要像缝 2 一样给出书面理由。

## Out of Scope

- **报价判断**：自动定价、工时估算、工艺路线生成（ADR-0001）。
- **全图尺寸还原**：只提取成本驱动的关键尺寸（ADR-0001）。
- **逐字段置信度**（ADR-0002）。
- **坐标级视觉定位**：bounding box 框选、点提取值高亮到原图（ADR-0004，验证成立后再做）。
- **漏提的系统性防御**：MVP 只靠并排原图 + 显式提示 + 人自查，不承诺替代看图（ADR-0004）。
- **私有化 / 本地部署**：只作销售话术与意向记录（ADR-0005）。
- **用户自助的导出字段映射 UI**：onboarding 手工配置（服务代替功能）。
- **实时模型优化 / 微调 / 自建提取管线**（ADR-0003）。
- **装配图、爆炸图**。
- **非目标零件族的质量承诺**：允许上传，标注"实验性、不保证"（ADR-0008）。
- **细粒度权限**：只有管理员 / 报价员两档；工艺、质量角色不在 MVP。
- 移动端原生应用、多语言、在线支付与订阅计费（试用费线下收取，ADR-0006）。

## Further Notes

- **有两个前置未决项，都需要调研而非拍板**：
  1. **目标零件族**是哪一族。ADR-0008 明确要求"先取 2~3 家目标工厂的真实图纸样本看分布再定"。提示词模板、风险规则库、fixture 图集都依赖这个结论。
  2. **多模态大模型供应商**。ADR-0003 与 ADR-0005 设了三条一票否决的硬门槛（数据存境内、书面承诺不用于训练、可签 DPA），且明确写了这三条先于识别效果。因此调研顺序是先核实合同条款筛掉不合格者，再在剩下的里面用真实样本比识别效果，结论另立一条 ADR。
  这两项都不阻塞后端主干开发（假引擎可先跑通），但都阻塞"能不能拿去给种子工厂用"。
- **验证目标**（ADR-0006）：三个月内用**处理耗时**对比人工基线证明省时，用向种子工厂**真实收取小额试用费**证明付费意愿。这两件事都需要产品内建支持（时间戳、基线录入、对比视图），已写进用户故事，不能当作运营的事情省掉。
- **ADR-0005 里提到的"模块 7 角色权限"** 对应本 spec 的权限与租户部分。它只解决内部越权访问；"图纸出厂上第三方云"的顾虑由供应商合同门槛解决，两者互补，不能互相替代。
- 本 spec 覆盖整个 MVP，篇幅上不适合当作单个 AFK 任务直接执行，应先拆成 `.scratch/mvp-quote-assistant/issues/NN-*.md`。建议的拆分顺序：目标零件族样本调研 → 大模型供应商合规调研 → 后端骨架与缝 1 测试基座 → 上传与分级 → 提取与信任规则 → 风险规则引擎（缝 2）→ 复核用例 → 报价任务与导出 → 修正记录与耗时 → 权限与租户 → 前端各页面 → 接入真实提取引擎。两项调研可与后端骨架并行，但真实引擎接入必须排在供应商结论之后。
- 未与任何现有 ADR 冲突。
