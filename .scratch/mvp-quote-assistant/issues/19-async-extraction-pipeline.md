# 19 — 异步读图取数：上传立即返回，分级与取数在后台跑

**What to build:** 把"分级 + **读图取数**"从上传请求的同步路径里挪出来。**报价员**批量拖进 10 张**零件图**后应当立刻看到列表，每张各自显示进行中状态并自行推进，而不是盯着一个转圈的上传按钮等到浏览器超时。

现在 `UploadPartDrawings.execute` 在一个请求、一个事务里串行做完"落盘 → 分级 → 取数"。假引擎瞬时返回，所以这个结构在缝 1 里毫无痛感；真实多模态大模型单张十几秒起步，一次传 10 张就是一个挂几分钟的 HTTP 请求，中间任何一个环节失败会把整批已落盘的图一起回滚掉。

用户故事 10「我想在提取进行中看到进度状态，以便我知道是在跑还是卡住了」其实已经预设了异步——前端也早就在轮询了（`ExtractionInProgress` 每秒 `router.refresh()`）。缺的只是后端把活儿真正放到请求之外。

**不引入 Redis / Celery。** MVP 的并发量是一家工厂的几个报价员，进程内后台执行加上启动时的滞留回收足够，多一套外部依赖只会多一处部署与运维成本。将来真需要横向扩容再换实现——作业提交同样走 Port，换实现不动用例层。

## Comments

- `PartDrawingProcessor.submit` 是用例层唯一看到的作业入口。实现有三个：`inline`（缝 1 / 默认测试）、`thread`（生产默认）、`DeferredPartDrawingProcessor`（测试用，提交后不跑，调用 `run_pending()` 才推进）。
- 上传用例现在只落盘并提交作业。`ProcessPartDrawing` 负责「没分级先分级，再取数」，重试按钮也走它——分级阶段就失败的图不会跳过劝退直接取数。
- 作业里的引擎和对象存储从 `app.state` 现读，缝 1 替换 `extraction_engine` 不必重建 processor。
- 启动回收覆盖「已上传 / 分级中 / 提取中」：进程重启后这三态都不可能还有人在跑。回收到「提取失败」，原因是「读图取数被中断（服务重启），请重试」。
- 前端列表对进行中状态每秒 refresh；详情在已上传 / 分级中 / 提取中显示进行中面板。「已分级」仍可由 `AutoStartExtraction` 补一刀（作业在分级提交后、取数开始前崩了的缝隙），409 当作已有人在跑。
- 验证：缝 1 `uv run pytest -m "not vendor_contract"` 139 passed / 1 deselected。前端 `tsc --noEmit` 通过。
